# 网络兼容状态：已修复公网多地址连接，代理主需求仍未完成

对应 Issue #23 / PR #24。PR仍为草稿；不要把本页或测试数量解释为全代理/TUN/VPN/虚拟机认证。main未被本PR修改。

## 本轮实际改变了什么

此前只连接DNS返回的第一个地址。如果首个IPv6不可达、第二个IPv4实际可达，也会整体失败。现在原HTTP与Chromium的Python网络桥都保留同一次查询的完整结果，在原有全部公网检查通过后，交错尝试IPv4/IPv6，最多4个候选，共享原有连接超时预算。

候选切换只发生在发送HTTP请求之前。证书不可信、TLS协议错误、操作系统权限拒绝时立即停止，不切代理、不关闭TLS。收到HTTP拒绝或发送/读取失败后，不重放请求，更不会重复提交POST。

这是真正的连接行为修复，不只是新增一个状态字段。它解决的是：**已有可用系统路由、DNS已返回公网地址，但程序错把首个IP失败当成整个网站不可达**。

本地受控TLS测试已经覆盖首个IPv6无路由→第二个IPv4成功、同族地址失败回退、POST只发送一次、403不换地址重试、错误证书不能通过。测试用显式mock把公网IP符号映射到本机测试服务器；生产没有该开关。测试证书只用于fixtures，绝不能安装为系统信任根。

## 仍然没有交付什么

- 真正消费HTTPS_PROXY/ALL_PROXY/系统静态代理并建立HTTP CONNECT或SOCKS5连接。
- Fake-IP识别后的可信代理解析/连接模式。198.18.*仍拒绝，不加入白名单。
- 虚拟机到宿主机代理的显式入口配置；不会猜网关或扫描局域网。
- 网页内网络模式、代理配置和完整路径测试。
- 用户实际VPN/TUN/虚拟机产品的现场认证。

此前该核心代理传输提交被工具安全检查拦截。本轮没有重新提交那份实现或通过别的工具绕过，而是修复独立的首地址连接缺陷。不要将这个较窄修复当成完成Issue #23的全部目标。

## 用户怎样判断是否适用

| 当前结果 | 本轮修复的作用 |
|---|---|
| DNS全为公网，但首个地址无法连接、另有地址可达 | 自动有限尝试其他已验证地址；无需增加表单字段 |
| TUN/VPN提供正常系统路由，DNS仍为真实公网地址 | 不需要关闭该路由；连接仍服从操作系统路由。只针对地址选择改进，不是产品实测保证 |
| DNS返回198.18.*、私网或混合公网/私网 | 仍按安全策略拒绝，本轮没有解决Fake-IP兼容 |
| 只有HTTP/SOCKS本机代理能出网，没有可用系统路由 | 当前仍未接入代理，不能宣称已可用 |
| 所有候选无路由、网站拒绝、账号无权或离线 | 如实失败，不伪造结果或绕过限制 |
| tls_verification_failed / tls_handshake_failed | TLS校验或协议失败，不再一律当普通网络错误；检查证书/系统配置，不关闭校验 |

使用修复分支完整源码后继续原启动命令，不需换Python或安装额外运行依赖。这个修复自动作用于原HTTP、搜索/案例和浏览器桥，不需另建代理设置。

## 原只读诊断仍可用

`scripts/check_network_environment.py`读取Python标准库可见的静态代理配置，不发DNS/TCP/HTTP、不修改设置。结果隐藏认证值，明确`collector_applies_static_proxy=false`。查到代理不等于已消费代理；查不到静态配置也不能推断TUN/VPN关闭。虚拟机里的127.0.0.1仍指虚拟机本身。
